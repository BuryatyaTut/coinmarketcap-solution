# Аутентификация API

Сервис использует один заранее настроенный секретный API-ключ. Клиент передаёт его в заголовке каждого запроса:

```http
Authorization: Bearer <APP_API_TOKEN>
```

Проверяется владение ключом, а не личность отдельного пользователя. Все клиенты с правильным ключом имеют одинаковый доступ ко всем операциям. Регистрация, выпуск JWT, пользовательские сессии и роли не входят в эту схему.

## Два разных ключа

| Переменная | Кто использует | Куда передаёт |
| --- | --- | --- |
| `APP_API_TOKEN` | Клиент нашего API | В наш сервис, заголовок `Authorization: Bearer …` |
| `CMC_API_KEY` | Наш сервис | В CoinMarketCap, заголовок `X-CMC_PRO_API_KEY` |

Ключ CoinMarketCap не выдаётся клиенту. Значения берутся из окружения; при `npm start` Node также загружает локальный `.env`, если он существует. В репозитории находится только шаблон `.env.example`.

## Путь запроса по коду

1. [config.ts](../src/config.ts), `loadConfig()`, читает `APP_API_TOKEN` и `CMC_API_KEY`. Ключ нашего API должен содержать 16–512 символов без пробелов. Совпадение двух ключей запрещено. Минимальная длина сама по себе не обеспечивает случайность: ключ нужно сгенерировать случайным образом.
2. [server.ts](../src/server.ts), `startServer()`, передаёт `config.apiToken` в `createApp()`.
3. [app.ts](../src/app.ts), `createApp()`, вычисляет SHA-256 от настроенного ключа и регистрирует общий middleware через `app.use()` до маршрутов. Middleware — обработчик, через который запрос проходит перед основной операцией.
4. Middleware читает `Authorization` и проверяет форму `Bearer <token>`. Для полученного значения вычисляется SHA-256, затем два 32-байтовых результата сравниваются встроенным `timingSafeEqual()`.
5. Если ключ отсутствует, формат неверен или значения не совпали, выполнение основной операции прекращается. Клиент получает `401`, `WWW-Authenticate: Bearer` и JSON-ошибку `UNAUTHORIZED` с идентификатором запроса.
6. Если ключ правильный, вызывается `next()`, и запрос проходит дальше к проверке входных данных и обработчику операции. Ошибки других проверок по-прежнему возможны: правильный ключ не делает некорректный запрос корректным.

SHA-256 здесь даёт результаты одинакового размера для сравнения. `timingSafeEqual()` сравнивает их без раннего выхода на первом различающемся байте. Это свойство сравнения, а не гарантия постоянного времени обработки всего HTTP-запроса. Хеширование не шифрует передаваемый ключ и не превращает его в JWT.

Пример отказа, где идентификатор запроса приведён условно:

```json
{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "A valid application Bearer token is required",
    "requestId": "example-request-id"
  }
}
```

Проверка общая для всех девяти операций, включая `GET /openapi.json`. При отказе основной обработчик не вызывается: запрос не меняет БД и не вызывает получение цены у провайдера.

## Проверки и границы

[tests/api.test.ts](../tests/api.test.ts) проверяет отсутствие ключа и неправильный ключ для всех операций, а успешный CRUD-сценарий — доступ с правильным ключом. [tests/config-validation.test.ts](../tests/config-validation.test.ts) проверяет конфигурацию, в том числе запрет совпадающих ключей. Схема описана также в [OpenAPI](openapi.json).

Сервис по умолчанию слушает только `127.0.0.1`. Если он размещается для удалённого доступа, Bearer token нужно передавать по HTTPS; встроенный сервер сам TLS не настраивает. Ключ действует, пока он указан в конфигурации. Для его замены требуется обновить окружение сервера, перезапустить сервис и обновить значение у клиентов. Отдельного отзыва ключа одного клиента и ограничения частоты входящих запросов в этой реализации нет.
